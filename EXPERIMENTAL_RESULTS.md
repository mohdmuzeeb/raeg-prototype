pilot, uses 3 seeds and 200 intents per run, and **no estimate meets the original precision target** (DESIGN §8.3).
Nothing here is interpolated or extrapolated to configurations that were not run.

## 2. Metrics (DESIGN §6.2)

The agent's claim for an action is that of its primary submission (copy 0). `E` is the number of succeeded payments
for the action in the provider's ledger (the oracle).

| Metric | Definition |
|---|---|
| Duplicate-effect action | `E ≥ 2`; excess effects = Σ max(0, E − 1) |
| Recovery completion | Among actions with an injected fault: a correct `SUCCESS` (E ≥ 1) or `NO_EFFECT` (E = 0) claim by the horizon. **A duplicated success counts as correct**, so this metric must always be read with the duplicate-effect count (pairing rule D9). |
| Unresolved | `UNRESOLVED(*)` claims. Never counted as failures. |
| False success / false failure | `SUCCESS ∧ E = 0` / `NO_EFFECT ∧ E ≥ 1` |
| Claim correctness | Correct claims / decided (`SUCCESS` or `NO_EFFECT`) claims |
| Accepted | The system answered at least one submission or poll for the intent |

**Confidence intervals** are 95%:
- computed by a two-stage cluster bootstrap (seeds, then actions within each seed), B = 10,000, with a fixed RNG seed;
- the exact Clopper–Pearson interval is reported instead whenever it is wider. With 3 seeds, a bootstrap can collapse to zero width, and that is never reported as precision.

**Observations, restricted to what the tables show:**
- **RAEG, both modes:**
  - 0 duplicate-effect actions, 0 false successes and 0 false failures in every cell;
  - every decided claim was correct;
  - on P1, P2 and P4, every faulted action was recovered;
  - on P6 (no idempotency, no lookup, no deadline), no faulted action was recovered; all were escalated as `UNRESOLVED`. This is the cost of Tier S safety the design anticipated (§6.2): no safe recovery exists on P6.
- **RAEG-strict vs RAEG-bounded:** identical outcomes in every M7 cell. No M7 cell exercises the conditions in which the two modes differ (the Tier B cells P4n and F7 were not run), so **this dataset cannot distinguish the two modes**.
- **Baselines that produced duplicate-effect actions:**
  - B1: on every provider, including F0, where all its duplicates come from F5 concurrent submissions (Table 3);
  - B2 and B3: on the providers without idempotency (P4, P6);
  - B3L-δ and B3L-horizon: on P6 only.
- **Baselines that recovered fewer faulted actions:** under FM on P1 and P2, B2 and B3 recovered fewer than the other systems, leaving actions `UNRESOLVED(gave_up_ambiguous)`.
- **False claims:** no system produced a false success or a false failure in any cell.

## 4. Validity notes and limitations

1. **Exploratory, under-powered study.** R = 3 seeds (crash cells: 1 seed), 200 intents per run, and 33–49 faulted actions per seed. The original precision target (R ≥ 5, ≥ 100 faulted actions per seed, CI half-width ≤ 3 pp) is **not met by any estimate** (Table 5), and it was not relaxed. With only 3 seeds, between-seed variance is poorly estimated.
2. **The pilot data were planned as calibration only.** DESIGN §8.3 excluded pilot data from paper tables, and every run manifest records `excluded_from_paper: true`. After M8 was cancelled, the owner decided to use this dataset, labelled exploratory (PROTOCOL_CHANGES PC-5). The manifests are left unaltered.
3. **Temporal latency is invalid** for B3, B3L-δ and B3L-horizon. The Temporal stack had no readiness check, so runs started before it was warm, and early actions waited up to ≈ 10 s (N58; Table 4 gives the measured extent). Their latency is not reported, and no new latency experiment was run. The fix (N60) exists in later code but was never used for any reported run.
   - Their safety and recovery outcomes showed no concentration in the warm-up window (N58). However, this was not tested formally.
4. **RAEG latency** includes a ≤ 20 ms poll of the recovery worker (N52).
5. **Scope.** The following were **not** run, so no claim is made about them:
   - providers P3, P5, P7 and P4n;
   - faults F2, F5-only, F6, F7, F8 and F10 as separate cells;
   - the V1–V4 assumption-violation runs, the Tier B table, the `/noDL` controls and the 4 ablations;
   - N > 200 and more seeds.
6. **Crash cells** (Table 6) use one seed and three crashes per run. They are counts only, without seed-level intervals.
   - For B1 and B2, the "worker" crash is an API-process crash, because they have no separate worker (PC-4).
7. **Synthetic setting.** The provider, its faults and its timing are synthetic and time-compressed (DESIGN §2.7a). Faults are injected deterministically and replayed identically for every system.
8. **Recovery completion counts duplicated successes as correct** (by definition). Rankings by recovery completion alone would favour B1; always read it with the duplicate-effect count.

## 6. Reproducing the analysis

```bash
# 1. place the archive at results/archive/pilot-20261011.tar.gz, then verify it
shasum -a 256 results/archive/pilot-20261011.tar.gz   # must equal 66da0511…c23a (§1)
# 2. regenerate every table, figure and the generated block above (about 1 min; deterministic, byte-identical)
uv sync --group analysis
uv run --group analysis python scripts/analyze_paper.py
```

The script:
- refuses to run if the archive hash differs, any file fails `SHA256SUMS`, any run is not complete or audited `pass`, or any run is from a different commit;
- reads only the extracted archive, never `results/raw/`.

To re-run the experiment itself (not needed for the paper):
1. `git checkout 6c7a2a7` (the published SHA of `235ffd0`; see `docs/COMMIT_MAP.md`)
2. `DOCKER_CONTEXT=colima RAEG_SLEEP_GUARD=caffeinate caffeinate -i -s uv run python -m harness.runner config/experiments/pilot.yaml`

The provider and fault plans are deterministic per seed. Wall-clock-dependent behaviour (latency, Temporal warm-up) is not.
